# Мониторинг инженерной инфраструктуры

Веб-сервис для мониторинга состояния датчиков инженерной инфраструктуры, анализа истории событий и формирования предупреждений о возможных проблемных эпизодах на горизонте 24 часов.

Проект разработан в рамках хакатона «Лидеры цифровой трансформации 2026».

## Возможности

Система позволяет:

- загружать журнал событий датчиков;
- загружать и сохранять справочники каналов и объектов;
- обрабатывать большие журналы событий;
- сопоставлять события с датчиками и объектами инфраструктуры;
- хранить нормализованную историю событий;
- рассчитывать признаки по истории работы датчиков;
- выполнять ML-инференс с использованием CatBoost;
- рассчитывать контрольный индекс риска;
- формировать предупреждения о потенциальных проблемных эпизодах;
- отображать датчики без предупреждения и датчики, для которых прогноз недоступен;
- искать датчики по ID, названию, типу или объекту;
- фильтровать датчики по состоянию;
- просматривать подробную карточку датчика;
- просматривать последнее зарегистрированное событие;
- просматривать историю событий;
- работать в светлой и тёмной теме.

# Запуск проекта

## Требования

Для запуска требуется:

- Docker Desktop или Docker Engine;
- Docker Compose;
- включённая аппаратная виртуализация.

Отдельно устанавливать Python, Node.js, npm, FastAPI, CatBoost и остальные зависимости не требуется — они устанавливаются внутри Docker-контейнеров.

## Первый запуск

Откройте терминал в корневой папке проекта и выполните:

```powershell
docker compose up --build -d
```

Проверить состояние контейнеров:

```powershell
docker compose ps
```

После запуска приложение доступно по адресу:

```text
http://localhost:5173
```

Backend API:

```text
http://localhost:8000
```

Документация FastAPI:

```text
http://localhost:8000/docs
```

## Последующие запуски

Если код не изменялся:

```powershell
docker compose up -d
```

Если код был изменён:

```powershell
docker compose down
docker compose up --build -d
```

Остановить приложение:

```powershell
docker compose down
```

# Загрузка данных

В интерфейсе нажмите:

```text
Загрузить данные
```

Система использует три типа входных файлов.

## Журнал событий

Обязательный файл.

Поддерживаются:

```text
.csv
.7z
```

Структура журнала:

```text
ид_события
ид_канала_данных
дата
время
тревожное
значение_датчика
```

Пример:

```csv
ид_события,ид_канала_данных,дата,время,тревожное,значение_датчика
1409185555,213358,2026-09-20,09:58:46,false,Норма
```

Для больших журналов рекомендуется использовать `.7z`.

В архиве должен находиться один CSV-файл журнала.

## Справочник каналов

Формат:

```text
.csv
```

Основные поля:

```text
ид_канала_данных
тип_инж_системы
тип_датчика
тег_инженерной_системы
название_датчика
ид_объект
```

Поле `ид_объект` используется для связи датчика с объектом инфраструктуры.

## Справочник объектов

Формат:

```text
.csv
```

Основные поля:

```text
ид_объект
иерархия_уровень
родитель
вид_объекта
диспетчерское_название_объекта
```

При последующих загрузках можно выбирать только новый журнал событий.

# Обработка данных

После загрузки система автоматически:

1. проверяет входные файлы;
2. нормализует журнал событий;
3. сопоставляет события с датчиками и объектами;
4. сохраняет историю событий;
5. рассчитывает признаки;
6. выполняет ML-инференс;
7. рассчитывает индекс риска;
8. сохраняет итоговые прогнозы.

Для больших журналов обработка может занимать несколько минут.

После завершения отображается:

```text
Готово
N событий · N прогнозов
```

---

# Категории датчиков

В интерфейсе используются три основные категории.

### Без предупреждения

Прогноз рассчитан, признаки повышенного риска не обнаружены.

### Предупреждение

Система обнаружила признаки повышенного риска проблемного эпизода.

### Без прогноза

Прогноз не может быть корректно рассчитан.

Возможные причины:

- недостаточно истории;
- отсутствуют события;
- данные устарели;
- недостаточно необходимого контекста для расчёта.

Для штатного прогноза рекомендуется иметь не менее 7 суток истории событий по датчику.

# Ограничения

ML-score представляет собой оценку модели для появления нового зарегистрированного проблемного эпизода в ближайшие 24 часа.

Он не является подтверждённой вероятностью физической поломки оборудования.

Качество результата зависит от:

- полноты истории событий;
- корректности справочников;
- частоты поступления данных;
- качества зарегистрированных состояний;
- соответствия новых данных данным, использованным при разработке модели.
