# Передача проекта команде: что сделано и как продолжать

## 1. Чем занимается проект

Проект анализирует журналы датчиков городской инфраструктуры. Конечная цель —
заранее предупреждать о новом устойчивом проблемном эпизоде. Однако до прогноза
нужно надёжно определить сами эпизоды. Поэтому текущая работа разделена на два слоя:

1. **Stage 1, детектор:** преобразует сырые сообщения в проверяемые события и
   выделяет объяснимые аномальные эпизоды.
2. **Будущий прогноз:** использует только прошлое до момента `t` и пытается
   предсказать начало нового подтверждённого эпизода в следующие 24 часа.

Существующий `ml/smoke_failure` — отдельный ранний эксперимент только для дымовых
датчиков. Он не заменяет Stage 1 и не доказывает физическую неисправность.

## 2. Полный путь данных

```text
CSV/7z журнал + справочник каналов
        ↓
потоковая нормализация и контроль качества
        ↓
NormalizedEvent: исходное значение, число, время, источник, флаги
        ↓
реестр типа датчика выбирает numeric/discrete обработку
        ↓
причинный detector: использует только доступное прошлое
        ↓
один или несколько Episode с start_at / confirmed_at / end_at
        ↓
агрегация, восстановление и подавление близких повторов
        ↓
каталог всех каналов и всех эпизодов
        ↓
синтетическая оценка тем же публичным pipeline
        ↓
решение готовности и будущая 24-часовая прогнозная разметка
```

`candidate` означает срабатывание технического правила, а не доказанную поломку.
`no_candidate` означает отсутствие искомого паттерна, а не исправность.
`unknown` означает, что данных или их качества недостаточно для решения.

## 3. Где находится логика

- `stage1/contracts.py` — контракты `NormalizedEvent` и `Episode`.
- `stage1/normalization.py` — разбор строк, дубликаты и конфликты.
- `stage1/observability.py` — пригодность временных окон без заполнения пропусков.
- `stage1/detectors.py` — numeric/discrete/context правила версии
  `stage1-baseline-v2`.
- `stage1/episodes.py` — объединение, восстановление и suppression.
- `stage1/pipeline.py` — единый публичный путь обработки канала.
- `stage1/evaluation.py` — сопоставление предупреждений с известными сценариями.
- `stage1/forecast_labels.py` — безопасная будущая метка без утечки.
- `stage1/verification.py` — исполняемые причинные инварианты готовности.
- `analysis/prepare_stage1_sample.py` — подготовка нормализованной выборки.
- `analysis/run_stage1_baseline.py` — каталог каналов со всеми эпизодами.
- `analysis/run_synthetic_benchmark.py` — оценка того же публичного pipeline.
- `analysis/build_stage1_examples.py` — трассируемые реальные примеры.
- `analysis/build_stage1_final_report.py` — итоговый статус готовности.

## 4. Текущий честный результат

- Реальная ограниченная выборка: 38 каналов, 19 типов, 7 групп.
- В ней сохранено 38 результатов: 7 `candidate`, 19 `no_candidate`, 12 `unknown`.
- Holdout: TP=5, FP=8, FN=0, F1=0,556.
- Tuning: TP=4, FP=39, FN=1, F1=0,167.
- Все сценарии исполняются реальным pipeline, но tuning проходит ожидания только
  для 7 из 9 сценариев.
- Методический этап, прогноз и эксплуатационная готовность пока не объявлены
  завершёнными.

Текущий holdout уже просмотрен при ревью. После следующей настройки правил нужен
новый заранее зафиксированный набор; использовать нынешний holdout для выбора
порогов нельзя.

## 5. Как развернуть проект

```powershell
git clone <URL-репозитория>
cd HacatonMSC2026
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
```

Данные в Git не входят. Их нужно передать команде отдельно и положить в `data/`.
Минимально нужен `справочник_каналов_датчиков.csv`; для полного прохода нужны
журналы CSV/7z за соответствующие годы.

## 6. Как проверить изменения

```powershell
python -m ruff check .
python -m ruff format --check .
python -X utf8 -m unittest discover -s stage1 -p "test_*.py" -v
python -X utf8 -m unittest discover -s analysis -p "test_*.py" -v
python -X utf8 -m unittest discover -s ml/smoke_failure -p "test_*.py" -v
```

Сгенерированные файлы находятся в `output/` и намеренно исключены из Git. Команды
их пересоздания приведены в `docs/stage1-reproducibility.md`.

## 7. Что добавлять в Git

В текущем репозитории почти весь новый код ещё не отслеживается. Для общего коммита
Stage 1 из корня проекта нужно выполнить:

```powershell
git add -- ".gitignore" "README.md" "pyproject.toml" `
  "requirements.txt" "requirements-dev.txt" ".github" `
  "stage1" "analysis" "docs" "ml"
git status --short
git diff --cached --stat
git diff --cached --check
```

Не добавлять:

- `data/` — исходные журналы;
- `output/` — генерируемые отчёты, модели и Parquet;
- `.venv/`, `.idea/`, кэши Python;
- архивы `.7z`, модели `.cbm`, временные файлы;
- `Город 8. ДЖКХ.pdf` — локальный исходный документ;
- `saw dataset.ipynb` — отдельный исследовательский notebook; добавлять только
  осознанным отдельным коммитом после очистки выводов и проверки секретов.

После просмотра staged diff:

```powershell
git commit -m "Add causal Stage 1 anomaly pipeline and review fixes"
git push -u origin <имя-ветки>
```

## 8. Как разделить следующую работу

1. Один участник анализирует 39 FP на tuning и предлагает изменения правил без
   просмотра нового holdout.
2. Второй строит полный исторический каталог и проверяет число независимых эпизодов,
   покрытие и нагрузку предупреждений по типам.
3. Третий готовит новый замороженный набор сценариев и запускает его один раз после
   фиксации следующей версии правил.
4. Отдельно требуется получить актуальный справочник `канал → объект` и внешнюю
   проверку части реальных кандидатов.
5. Только затем можно строить пары «признаки до `t` → новый эпизод после `t`» и
   сравнивать прогнозное правило с ML.

Каждое изменение детектора должно повышать `RULESET_VERSION`, сопровождаться тестом
на найденный контрпример и пересчётом tuning. Новый holdout нельзя использовать как
итерационный tuning-набор.
