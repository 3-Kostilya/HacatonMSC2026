# M1 / A1 — полный ingestion доступной истории

Статус на 2026-09-23: **техническая часть A1 завершена**. Опубликованный
артефакт: `output/milestone1/full_20260922/` с `manifest.json` в состоянии
`status=complete`. Совместная приёмка M1 ещё требует независимой проверки B1.

## Что обработано

Обработаны пример журнала и все семь предоставленных архивов: 2019, 2020,
2022, 2023, 2024, 2025, 2026. Архива 2021 года нет; этот период не
восстанавливался. Все восемь источников и оба справочника записаны в manifest
с размерами и SHA-256. Ограничений `max_rows` в полном прогоне нет.

| Повторных `event_id` среди clean | 2 752 671 |

Баланс: `259 453 121 + 563 940 + 1 = 260 017 062`. Повторный `event_id`
сам по себе не служит основанием для удаления строки: удаляются только точные
дубли по согласованному ключу. Два справочника содержат 11 485 каналов и
95 объектов. В исходном справочнике каналов нет ключа «канал → объект»;
поэтому 253 337 159 известных clean-строк имеют статус
`object_mapping_unavailable`, а 6 115 962 — `unknown_channel`.
Объектные связи не выводились из названий или тегов.

Распределения по типам датчиков, месяцам, связям и флагам находятся в
`data_quality.json`; краткая таблица семейств — в `sensor_family_report.csv`.
`clean/year=*/month=*/data_0.parquet` отсортирован по
`channel_id, timestamp, row_id` внутри каждого файла. Конкатенация всех
разделов не является одним глобально отсортированным потоком.

## Проверки и воспроизводимость

Внутренние проверки подтвердили сохранение числа строк, отсутствие
размножения при соединении со справочниками, корректное представление значений,
уникальность `(source, source_row)` в clean, точное число Parquet-строк и
сортировку **каждой** принятой строки. Независимый `--deep` verifier повторно
сверил SHA-256 всех источников, физические Parquet, 79 разделов, число
исключённых строк и пересчитал типы, связи и календарь из clean.

Отдельное логическое сравнение рабочей DuckDB и опубликованных Parquet по
всем экспортируемым колонкам прошло для 79 clean-разделов,
`excluded_rows.parquet` и `sensor_statistics.parquet`. Результат находится в
`output/milestone1/full_20260922_logical_fingerprint.json` (локальный файл,
не для Git). Для сравнения использованы два независимых хеша строк и несколько
агрегатов; это проверка равенства мультимножеств, не криптографическое
доказательство каждой строки.

Для B создан `output/milestone1/b1_full_sample.parquet`: 213 строк, 24 022
байта. Детерминированный отбор охватил все 56 наблюдаемых категорий типа,
вида значения, связи, тревоги и флагов; непокрытых категорий нет. SHA-256
образца: `f67cf0a6f20b18eca5546232c476281e2454430ed73a0182bee5a1e51182c6df`.
SHA-256 исходного manifest для отбора:
`2fc2a1fd534e3c1bb33947c358c973a28698140732700f5778cc507dfb65bed0`.
Состав выборки записан в соседнем
`b1_full_sample.report.json`.

## Ресурсы и восстановление

Успешная финализация сохранённой базы заняла 660,6 с. Полное календарное
время от первого старта до публикации — 16,09 ч: оно включает две остановки,
ожидание и патологически медленное соединение в старом запросе исключённых
дублей. Причина последнего обнаружена через `EXPLAIN`: `BLOCKWISE_NL_JOIN`
заменён эквивалентным `HASH_JOIN`; новая версия быстро извлекла все
563 941 исключённую строку. Это время не следует выдавать за производительность
исправленного запуска с нуля.

Рабочая DuckDB перед публикацией занимала 24 998 064 128 байт (23,28 ГиБ);
наблюдавшийся пик рабочего набора процесса успешной финализации — около
8,9 ГиБ. Путь `output/milestone1/full_20260922.verify.duckdb` — временная
локальная ссылка на проверочную базу, которая не входит в публикуемый
артефакт. Код сохраняет checkpoint при загрузке, фиксирует выбранную стратегию
классификации до её запуска и умеет безопасно возобновлять загрузку,
финализацию производных таблиц и позднюю публикацию.

## Передача B

Передать B завершённые `manifest.json`, `data_quality.json`, схему из
`stage1/ingestion/schemas.py` и небольшой детерминированный фрагмент Parquet.
Скрипт для его пересоздания:

```powershell
.\.venv\Scripts\python.exe -X utf8 analysis/build_m1_handoff_sample.py output/milestone1/full_20260922 output/milestone1/b1_full_sample.parquet --max-rows 512
```

Большие данные и модели не коммитятся в Git по общему плану. B может получить
те же исходники и выполнить указанную команду полного прогона, затем сравнить
логические распределения и версии. Выборка и отчёты в `output/` локальные;
при передаче файлами их следует отправить через согласованный командой канал.
Для удобства создан локальный `output/milestone1/m1-a1-handoff.zip` (35 270
байт, SHA-256
`02cc5912e9e1d8998513d45b1e34afa65864abe881f4254dee09d9f3f8d2fb62`):
он содержит manifest, отчёт качества, таблицу семейств, выборку и её отчёт,
а также логическую сверку. Полные 4,29 ГиБ clean Parquet в ZIP не входят.
После независимого B1 обе стороны совместно принимают M1 и только затем
переходят к A2/B2.

### Что нужно согласовать перед общей приёмкой

В опубликованном B1-отчёте `docs/ml-m1-b-review.md` участник B описал другой
локальный комплект исходников: в его справочнике каналов присутствует
`ид_объект`, а в проверенном здесь справочнике этого поля нет. Поэтому B1 на
его ограниченной выборке нельзя считать независимой проверкой именно этого
полного артефакта. B должен получить те же файлы, сверить SHA-256 восьми
источников и двух справочников с `manifest.json`, затем запустить
`analysis/audit_m1_handoff.py` на опубликованном полном результате A. Сейчас
аудитор B читает абсолютные пути из manifest, поэтому запускать его нужно в
окружении, где именно эти пути доступны, либо предварительно согласовать с B
безопасное отображение путей при сохранении проверки хешей.
Если команда решит использовать комплект B с объектными связями как основной,
потребуется отдельный полный прогон A1 с ним и новый manifest.
