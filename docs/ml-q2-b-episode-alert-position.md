# Q2/B: позиция по коротким эпизодам и повторным предупреждениям

Дата: 27.09.2026. **Позиция стороны B для согласования с A и заказчиком, не новое утверждённое правило и не разрешение на живые предупреждения.** Основание: [техническая приёмка Q2/A](ml-q2-a-b-acceptance-and-oracle-review.md), [независимая сверка потолка B](ml-q2-b-oracle-acceptance.md) и [вопросы A](ml-q2-episode-alert-questions.md).

## Что B считает неизменным

1. Основная исследовательская цель остаётся прежней: будущая **зарегистрированная** запись «Неисправен» на канале, а не доказанная физическая поломка. Precision считается по самостоятельным выданным предупреждениям, Recall — по **всем назначенным** новым эпизодам периода, в том числе без допустимого часа прогноза. Одно предупреждение может сопоставиться максимум с одним эпизодом. `unknown`/`excluded` не становятся отрицательными метками. Замороженный R6, прежний открытый test и опубликованный Q2 не переписываем.
2. Пока действует принятый [контракт R1](ml-r1-operational-accepted.md): одно более позднее точное «Норма» того же канала без конфликта закрывает зарегистрированный эпизод; последующее уверенное «Неисправен» — новый зарегистрированный эпизод. Короткую последовательность нельзя автоматически объединить по удобному временному порогу. Один такой эпизод не равен доказанной новой физической поломке.
3. Разные состояния в одну секунду — конфликт, порядок `row_id` не разрешает его. На спорном температурном канале QA-запрет сохраняется. Молчание, `alarm=false`, числа и иные тексты сами по себе не подтверждают восстановление. Синхронные газовые сообщения не помечаем обслуживанием и не удаляем из оценки без внешнего свидетельства.

## Предложение B для отдельной версии правила предупреждений

**Текущий контроль:** не чаще одного предупреждения на канал в течение 24 часов независимо от дальнейших записей. Именно при нём оракул с известным будущим нашёл максимум **1 116 / 2 142 = 52,10%**. Для `Recall > 0,5` нужны минимум 1 072 обнаружения — 96,06% идеальной ёмкости. Это слишком узкий запас для обещания цели только улучшением признаков/модели.

**Кандидат для совместной офлайн-проверки, без включения в Q2:** досрочно снять подавление на канале только тогда, когда **после предыдущего предупреждения** уже наблюдалось уверенное новое начало «Неисправен» по R1 в его 24-часовом горизонте, затем на том же канале появилось более позднее бесконфликтное «Норма», и на новом часе канал опять пригоден к прогнозу. Все три факта должны быть известны к моменту нового решения. Если такого начала не наблюдалось, восстановление не подтверждено, есть конфликт или история неполна, 24-часовое подавление остаётся. Повторный балл/предупреждение относится к риску **следующего** эпизода; прошлому эпизоду второй TP не начисляется. Точный лимит операторской нагрузки и действие по повтору требуют ответа заказчика до эксплуатационного применения.

Это предложение мотивировано семантикой «наблюдаемое восстановление → новый риск», а не подгонкой метрики. Оно ещё не доказывает роста Precision или Recall: дополнительных ложных предупреждений может стать больше. Правило B3 об уведомлении после восстановления *аномалии* относится к другому объекту и само по себе не утверждает этот вариант для Q2.

## Что просим проверить у A

1. На реальных трассах по типам проверить, означает ли последовательность «Неисправен → Норма → Неисправен» два различимых зарегистрированных состояния для оператора, особенно при коротких возвратах. Если источник даёт более точный ключ устройства/состояния или сведения об обслуживании, указать их и время доступности. Пока внешнего ответа нет, R1-эпизоды остаются неизменными.
2. Подтвердить, что условие досрочного снятия подавления можно вычислить **только по прошлым сообщениям** и оно не сработает на конфликтной секунде, старой/неполной истории либо после предупреждения без наблюдавшегося эпизода. Проверить перенос состояния через месяц и перезапуск, без переноса через исключённый календарный разрыв.
3. Для неизменных меток и одинаковых сохранённых баллов сравнить старое правило и кандидат: полный знаменатель Recall, Precision по предупреждениям, разбивку по типам и месяцам, повторные/лишние предупреждения, нагрузку на 1000 канал-дней и на каждый канал, долю предупреждений вскоре после восстановления. Не выбирать вариант и порог по уже просмотренной validation; исследовательскую таблицу на ней можно показать только с этой оговоркой. Новое правило сначала версионировать и проверить на внутренних временных частях train.
4. Перед изменением самой семантики эпизода или эксплуатационного лимита получить предметное решение заказчика с примерами и допустимыми действиями оператора. Если заказчику нужны физические отказы, понадобится отдельное подтверждение исходов и новый target.

**Предлагаемая развилка:** если A подтверждает причинную реализуемость кандидата, B готовит отдельный офлайн-протокол сравнения правил предупреждений; R1/B3/Q2/R6 сохраняются как опубликованная база. Если A обнаружит неоднозначность восстановления, сохраняем действующие 24 часа и сначала уточняем источник и предметные правила. Целевые метрики считаем достигнутыми только после фиксации правил и проверки на новых независимых данных.
