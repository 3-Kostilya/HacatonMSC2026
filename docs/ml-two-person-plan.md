# План разработки ML-решения для двух участников

## Объём и принятые решения

Этот документ распределяет между двумя разработчиками ML-часть приложенного ТЗ:
данные → временные признаки → статистические методы / IsolationForest /
кластеризация / смены режима → синтетическая проверка → псевдоэпизоды →
прогноз на 24 часа → сравнение моделей и воспроизводимый inference.
Веб-интерфейс, REST API, карта, пользователи и заявки в объём не входят.
Графики нужны как исследовательские отчёты, а не как отдельное приложение.

У участников сопоставимый опыт, оба имеют доступ ко всем исходным архивам.
Дедлайн не определяет содержание плана. Рассматриваются все типы каналов;
непригодность конкретного метода для типа фиксируется явно. Маленькая выборка
используется для проверки кода, а не заменяет заявленный охват.

Кластеризация понимается именно как в ТЗ: один объект — временное окно канала,
модели обучаются внутри совместимых типов датчиков. Сравниваются MiniBatchKMeans
и HDBSCAN; сохраняются режим, расстояние/мера нетипичности, размер и редкость
кластера, затем переходы между режимами. Кластеризация самих датчиков не является
основной задачей. Номер кластера, редкость и статус шума HDBSCAN не являются target.
Для методов без сопоставимого расстояния поле не заполняется выдуманным значением:
контракт содержит название меры и статус её доступности.

Итоговый прогноз относится к началу определённого псевдоэпизода в будущем окне,
а не к подтверждённой физической поломке. Реальной эталонной разметки отказов нет.

## Ответственность

**Участник A — ты:** данные, часовые признаки, персональные профили,
статистические детекторы, кластеризация/IsolationForest, сквозной расчёт признаков.

**Участник B — друг:** синтетика и независимая оценка, автомат эпизодов,
слабая разметка, прогнозная выборка, baseline/Logistic Regression/CatBoost,
оценка прогнозов и калибровка.

Это не последовательность «A делает всё, B ждёт». B начинает с испытательного
набора и тестов будущей разметки на небольших фиксированных таблицах, пока A
готовит реальные признаки. Затем B проверяет первые детекторы, пока A добавляет
кластеризацию. Реальное обучение прогноза начинается только после допуска разметчика.
Написать интерфейс модуля заранее можно; объявлять качество по заглушкам нельзя.

| Общий этап | Участник A | Участник B | Точка объединения |
|---|---|---|---|
| M0 Договорённости | Схемы событий/признаков/оценок | Схемы эпизодов/target/прогноза и протокол оценки | Версия контрактов и общая маленькая выборка |
| M1 Данные | Проверка и масштабирование существующего ingestion | Независимые проверки данных, испытательные сценарии | Согласованный чистый Parquet и отчёт |
| M2 Признаки | Часовая сетка, окна, baseline, доступный контекст | Проверка причинности/наблюдаемости, генератор синтетики | Таблица признаков и проверенные 20 каналов |
| M3 Детекторы | Статистика, IF, кластеры, переходы, change point | Оценка отдельных правил и автомат эпизодов | Версионированные scores и эпизоды |
| M4 Проверка | Исправления по tuning, заморозка методов | Независимая синтетическая оценка и отчёт | Решение о допуске по каждому типу/методу |
| M5 Псевдометки | Причинный общий score и полный расчёт scores | Правила high-confidence, normal/unknown, каталог эпизодов | Замороженный разметчик и 50 примеров |
| M6 Прогноз | Подготовка пакетов признаков и адаптер inference | Target, временные split, baseline/LR/CatBoost | Проверенные прогнозы на validation |
| M7 Итог | Ablation и масштабирование расчёта | Порог, калибровка, закрытый тест и объяснения | Единый пакет моделей, метрик и команд |

## От чего стартуем

Существующий код сначала проверяется и переиспользуется, а не переписывается.
Наличие файла не означает соответствие новому ТЗ.

| Уже есть | Как использовать | Что остаётся |
|---|---|---|
| `stage1/ingestion/`, `analysis/prepare_ingestion.py` | Основа M1, чтение пакетами и DuckDB/Parquet | Полный прогон, ресурсы, проверка на полном объёме |
| Реальный прогон M1 на 869 993 строках | Регрессионная точка: 5 194 канала, 16 разделов | Не считать обработанными 313 млн строк |
| `stage1/registry.py`, `profiles.py`, `observability.py` | Типы, пригодность, правила наблюдаемости | Согласование с часовой сеткой и всеми семействами |
| `detectors.py`, `pipeline.py`, `episodes.py` | Статистический baseline и объединение | Исправить короткую статичную опору, дробление, отдельные drift/variance |
| `simulation.py`, `evaluation.py`, `verification.py` | Генератор, сопоставление, причинные проверки | Независимые фоны, отдельная проверка вида аномалии и прогноза |
| `forecast_labels.py` | Проверить и расширить временную семантику | Новая псевдоцель и согласование с подтверждением/наблюдаемостью |
| `ml/smoke_failure/` | Только пример организации обучения/артефактов | Не переносить автоматически старый target «Неисправен» |

Старый просмотренный holdout используется только как регрессионный набор.
Новое решение нельзя подбирать по нему и называть независимо проверенным.

## M0. Зафиксировать границы до параллельной разработки

**Совместно, владельцы контрактов указаны ниже.**

1. Зафиксировать общую Git-ревизию существующего кода. Незакоммиченные изменения
   ingestion должны попасть в общую базу после ревью, иначе у друга будет другая версия.
2. Создать воспроизводимую маленькую выборку и искусственные примеры всех важных
   режимов: numeric/state/mixed, unknown, пропуск, конфликт, новый канал, два эпизода.
3. B описывает временное разделение и синтетические tuning/holdout до подбора
   преобразований. Конкретные границы периодов выбираются после аудита покрытия,
   а не копируются вслепую из старого исследования дымовых датчиков.
4. A и B фиксируют схемы ниже, определения времени и недоступного результата.
5. Для каждого семейства заранее записать бюджет ложных эпизодов, допустимую задержку,
   минимальное покрытие и целевую полноту. Числа обосновать постановкой сценариев;
   не подбирать критерий допуска после просмотра теста. Для прогноза ориентиры
   исходного задания Precision > 0,7 и Recall > 0,5 — цели, а не обещанный результат.

**Передаваемые таблицы:**

| Артефакт | Основные поля | Кто выпускает |
|---|---|---|
| `clean/*.parquet` | Исходные поля, channel_id, timestamp, alarm, numeric/state, тип, object_id?, quality_flags, provenance | A |
| `hourly_features/*.parquet` | channel_id, prediction_time, тип, окна 1/6/24/168h, признаки, число наблюдений, доступность/причины | A |
| `anomaly_scores/*.parquet` | channel_id, as_of, оценки отдельных методов, cluster_id?, переходы, версии, доступность | A |
| `pseudo_failure_episodes.parquet` | episode_id, channel_id, kind, start_at, confirmed_at, end_at?, evidence, labeler_version | B |
| `training_dataset/*.parquet` | channel_id, prediction_time, horizon_hours, разрешённые признаки, target 0/1/null, eligibility, split, episode_id для аудита | B |
| `predictions.parquet` | channel_id, prediction_time, horizon_hours, score, probability?, risk_level?, status, model_version | B |

Крупные таблицы партиционируются; запись `*.parquet` не требует одного огромного файла.
Схемы получают версию, поля — фиксированные типы, все артефакты — `run_id`, хеш
конфига и происхождение. Уникальный ключ признаков — `(channel_id, prediction_time)`;
оценок — этот ключ плюс версия метода; прогноза — плюс горизонт и версия модели.

Время — локальное время журнала без самовольного присвоения UTC. Для снимка в t
окно признаков `(t-W,t]`, прогнозное окно `(t,t+H]`. Изменение этой конвенции
требует версии и граничных тестов. Недоступные значения остаются null со статусом,
а не превращаются в нулевой риск. Столбцы split/episode_id/provenance не входят
в разрешённый список ML-признаков.

**Приёмка M0:** оба читают одну и ту же тестовую таблицу, тесты ключей/типов/
временных границ проходят. После этого каждый может независимо писать свой модуль.

## M1. Данные: завершить существующую основу

**A1 — загрузка и масштаб.** Вход: текущий ingestion и исходные файлы.
Проверить ограниченный прогон, затем обработать всю доступную историю пакетами.
Сохранить число строк по источникам/месяцам, exact duplicates, повторные ID,
карантин, неизвестные каналы, размеры и ресурсы. Проверить свободный диск,
временные таблицы и поведение при остановке; промежуточный результат не выдавать
за завершённый. Если для полного масштаба требуется возобновление, добавить его
как отдельную задачу, не обходить ограничение загрузкой истории в RAM.

**B1 — независимый аудит и стенд.** Параллельно на исходниках и маленькой выборке:
проверить схему, связи, сохранение специальных чисел и текстовых состояний,
невозможность удаления по одному event_id. Подготовить список положительных
сценариев/отрицательных контролей и тесты ожидаемых артефактов.

**Передача A → B:** завершённый manifest, отчёт качества, схема и небольшой
детерминированный фрагмент Parquet. Большие файлы каждый может получить локально
одинаковой командой; сравнивать логическое содержимое и версии, не только байты файлов.

**Приёмка:** баланс всех строк, отсутствие размножения при join, сортировка,
полный аудит фактически доступных источников. 2021 отсутствует — указать как пробел,
не обещать полный период 2019–2026. После этого согласовать результат M1.

## M2. Часовые признаки и синтетический стенд

**A2.1 — сетка и наблюдаемость.** Строить channel × hour в ограниченных разделах;
хранить число событий, возраст последнего сообщения, пропуски и вычислимость.
Не заполнять молчание датчика нулями. Для регистрации только изменений отсутствие
события не считать автоматически потерей связи. Не создавать всю декартову сетку
каналы × все годы в оперативной памяти.

**A2.2 — окна и персональная опора.** События/тревоги/интервалы/смены состояний;
для numeric — median, MAD, IQR, std, квантили, диапазон, изменения и наклон
по реальному времени. Окна 1h/6h/24h/7d. Смешанные каналы сохраняют обе ветви.
Опора использует только прошлое, исключает текущий проверяемый интервал, имеет
прогрев, задержку допуска новых точек и защиту от поглощения дрейфа. «Не было
срабатывания» не является доказательством чистоты прошлого.

**A2.3 — контекст.** Предусмотреть peer/object-признаки, но вычислять только
при настоящем соответствии канал → объект и достаточном числе совместимых соседей.
Сейчас связи нет: фиксировать `unavailable`, продолжать self-признаки. Сравнение
по всем каналам одного типа не подменяет сравнение соседей одного объекта.

**B2.1 — генератор.** Переиспользовать `simulation.py`, добавить drift, bias,
variance, stuck, dropout, деградацию связи, переключения. Контроли: обычный шум,
сезонность, штатные циклы, единичный spike, общая смена среды, пропуск выгрузки.
Не объявлять реальный фон заведомо нормальным без оснований; идеальный синтетический
фон и реалистичные фрагменты без истины оценивать раздельно.

**B2.2 — независимые тесты признаков.** Ручной расчёт на коротких рядах,
границы часов, изменение частоты регистрации, пустые окна, MAD=0, невалидная
история. Добавление событий после t не меняет признаки в t. Проверить 20 каналов:
зафиксированная случайная выборка с представленными применимыми семействами
и особыми случаями; нехватку покрытия явно показать.

**Передача A → B:** версия признаков, таблица, маски пригодности, отчёт.
**Передача B → A:** воспроизводимые сценарии и обнаруженные нарушения контракта.
**Приёмка:** согласованные признаки/статусы и проверенные 20 каналов.

## M3. Детекторы, кластеры и эпизоды

**A3.1 — статистическая основа.** Заменить короткую неизменную опору числового
правила на проверенный причинный профиль. Разделить устойчивый сдвиг уровня,
дрейф и рост разброса. Добавить rolling change / CUSUM с причинным состоянием;
исключить двойное толкование обычного тренда как дисперсии без проверки.
Согласовать окно переключений со смыслом сценария, не ускорять генератор только
ради прохождения теста. План деталей: `docs/detector-improvement-plan.md`.

**A3.2 — IF и кластеризация.** Отдельный preprocessing внутри совместимого типа,
явный список признаков, контроль вкладов часто пишущих каналов. Сравнить
MiniBatchKMeans и HDBSCAN на одинаковой доступной выборке. Масштабировать подбор
через ограниченную стратифицированную обучающую выборку, а не HDBSCAN на всей
истории в RAM. Число кластеров и параметры выбирать на development.

Для новых окон нужен определённый способ присвоения режима без повторного обучения
на будущем. Если вариант HDBSCAN не обеспечивает такой путь, оставить его
исследовательским сравнением и не включать его признаки в причинный прогноз.
Номер режима не имеет порядкового смысла. При переобучении ID могут поменяться:
хранить версию модели, не считать смену нумерации физическим переходом.

**A3.3 — переходы и scores.** `previous_cluster`, `cluster_changed`, время в
режиме, число смен за 24h, частота переходов и рост расстояния. Для train размер
и редкость кластера берутся из допустимого обучающего прошлого, не из полного test.
Сохранять отдельные оценки до объединения; нормализаторы обучать без будущего.

**B3.1 — автомат эпизодов.** Несколько наблюдений/время для подтверждения,
отдельные пороги входа и восстановления, гистерезис, объединение близких фрагментов.
Не закрывать эпизод по одной нормальной точке и не создавать повторное уведомление
на каждом колебании. Уведомления и эпизоды хранить раздельно; cooldown не должен
скрывать новый эпизод после восстановления. Сохранять start_at и confirmed_at отдельно.

**B3.2 — оценка по контракту.** Пока A пишет модели, тестировать автомат на
искусственных последовательностях scores. После появления baseline подключить
тот же код к реальным результатам. Проверять обнаружение воздействия и правильность
его вида отдельно: срабатывание уровня на росте разброса не доказывает variance detector.

**Приёмка:** причинные scores и эпизоды, графики отдельных каналов, сравнение
статистики/IF/кластеров/change point. Это ещё не разрешение на массовые псевдометки.

## M4. Независимая проверка методов

**A4:** исправлять правила только по tuning; сравнить исходный метод, автомат
эпизодов, новый профиль, отдельные детекторы, IF/кластеры. Сохранять конфигурации
и одинаковые знаменатели. Заморозить код, параметры и preprocessing для приёмки.

**B4:** сформировать новый непросмотренный holdout: непересекающиеся фоновые
фрагменты, каналы/эпизоды и отложенные сочетания воздействий. Одной смены seed
недостаточно. Изолировать эталонные метки от признаков. Запускать holdout после
заморозки A; не раскрывать частные примеры для последовательной подгонки.

Отчёт: episode Precision/Recall/F1, задержка обнаружения/восстановления,
FP на наблюдаемые канало-дни, повторные уведомления, правильность вида воздействия,
покрытие и unknown, результаты по типам и фоновым семействам.
При no-ground-truth real data — нагрузка кандидатами и объяснимость, а не «реальный FP».

**Приёмка:** соблюдены заранее зафиксированные критерии по применимым группам.
Если нет — вернуться к A3/B3. После просмотра holdout и новых исправлений он
становится регрессионным, следующий финальный набор должен быть новым.

## M5. Слабая разметка

**A5:** объединять пригодные оценки в причинный anomaly score, сохранять состав
свидетельств и недоступные компоненты. Начать с прозрачных весов; метод обработки
пропущенных компонент фиксировать отдельно, чтобы высокий score не возникал от
изменения доступности. Выполнить расчёт для заявленного исторического периода.

**B5:** поверх допущенных методов построить high-confidence эпизоды:
устойчивость + дополнительные свидетельства по правилам вида аномалии.
Не приравнивать `Неисправен`, `alarm`, любой выброс или редкий кластер к отказу.
Вне уверенных positive/normal оставлять unknown. Общие события учитывать отдельно
при наличии настоящих объектных связей; отсутствие связи явно ограничивает вывод.

**Совместно:** проверить 50 случайных positive-эпизодов с прошлой и последующей
историей, дополнительно контрольные normal/unknown и покрытие типов. Это проверка
метода и объяснений разработчиками, не экспертное подтверждение физической поломки.

**Приёмка:** замороженные определение цели и версия разметчика, каталог всех
эпизодов и статистика positive/normal/unknown. Недостаточно меток в типе — статус
`insufficient_evidence`, не обучение на выдуманных отрицательных.

## M6. Прогноз будущего эпизода

**B6.1 — target.** H=24h, конфиг допускает 6/12/48h. `target=1`, если новое
начало находится в `(t,t+H]`; `0` — только при достаточной будущей наблюдаемости
и отсутствии целевого начала; иначе null. Уже начавшийся эпизод исключается
из задачи предсказания нового начала. Подтверждение может быть позже start_at:
выделить необходимый последующий период проверки метки и учесть его на границах split.
Длительность и будущие свидетельства эпизода не являются признаками в t.

**B6.2 — разбиение.** Только временные train/validation/test, purge по реальному
интервалу зависимости метки, один эпизод не разносится между split, контролируемое
число positive snapshots, cooldown и наблюдаемость. Балансировку делать только
на train; test сохраняет естественную частоту событий в объявленной популяции.

**Совместный критический контракт:** fit scaler/imputer/IF/кластеров/score-нормализатора
и правила обучения разметчика — только на разрешённой прошлой части каждого
эксперимента. Для прогнозного train использовать хронологические out-of-fold scores
либо отдельный ранний период обучения детектора. Нельзя обучить кластеризацию на
всей истории и затем назвать полученные train-признаки причинными.

**B6.3 — обучение.** На одинаковых допустимых примерах сравнить anomaly-score
baseline, простое правило истории, Logistic Regression и CatBoost. Проверить
дисбаланс, оба класса, метрики по типам. Почти идеальное качество запускает аудит
утечки, а не автоматическое объявление успеха. Контроль: внезапное воздействие
без предвестника не засчитывается как успешно предсказанное после его начала.

**A6 — поддержка параллельно.** Генерировать версионированные пакеты признаков для
фолдов, проверять равенство batch/replay на одних префиксах, писать причинный
адаптер расчёта для `prediction_time`. Не менять feature schema молча во время
обучения друга. Пока идёт обучение, профилировать большие разделы и память.

**Приёмка:** воспроизводимая прогнозная выборка, аудит утечки, сравнение baseline
и ML на validation. Все метрики относятся к определённым псевдоэпизодам.

## M7. Выбор решения и финальный расчёт

**A7 — ablation.** На одинаковых split и наблюдаемой популяции сравнить rolling;
+ anomaly; + clusters/transitions; + change point; + weak states; + peer/object
при наличии данных; full. Фиксировать также отрицательный результат кластеризации:
её наличие в эксперименте не требует оставлять её в финальной модели.
Недоступные peer/object отметить N/A, не заменять синтетической привязкой.

**B7 — пороги и объяснения.** Выбирать порог и LOW/MEDIUM/HIGH на validation,
калибровку — на отдельной допустимой части/хронологических фолдах. Не обещать
вероятность физической поломки: при слабой калибровке возвращать score и статус.
Сохранить feature importance и SHAP на ограниченной выборке с примерами факторов.

**B7 — закрытый тест.** После фиксации вариантов, порога и модели выполнить
финальную оценку: PR-AUC, Precision/Recall, эпизодное сопоставление, ложные
предупреждения на наблюдаемые дни, упреждение, покрытие/unknown, числа эпизодов,
метрики по типам и интервалы неопределённости. Один эпизод — один TP, повторы
показаны отдельно. Упреждение в оценке H=24h ограничено 24 часами; для «раньше
24h» нужен отдельный H=48h эксперимент, не изменение смысла основного показателя.

**A + B — inference.** A отвечает за путь история → признаки/оценки; B — за
признаки → прогноз и сериализацию модели. Единый вызов принимает данные, t,
горизонт и пакет моделей, выдаёт таблицу predictions с причинами недоступности.
Не обучается заново и не читает всю историю при каждом прогнозе. Пакет включает
схему, preprocessing, детекторы, кластеры, разметчик, модель, пороги и версии.

**Итог:** команды подготовки/оценки/обучения/inference, данные промежуточных
этапов, `metrics.json`, таблица ablation, объяснения, прогнозы и общий отчёт.
Замерять время, память и объём обработки; ориентир расчёта <5 минут относится
к описанному прогретому inference, а не к загрузке всей истории и обучению.
Если CatBoost проигрывает baseline или отдельный тип не пригоден, это допустимый
исследовательский вывод, но не объявленная успешная модель для этого типа.

## Границы файлов и объединение работы

Новые директории ниже — план размещения; создавать их нужно в своём подэтапе.

| Владелец | Зона изменений |
|---|---|
| A | `stage1/ingestion/`, `stage1/features/` (новая), `stage1/anomaly_models/` (новая), `profiles.py`, `detectors.py`, основной `stage1/pipeline.py`, скрипты подготовки данных/признаков |
| B | `simulation.py`, `evaluation.py`, `verification.py`, `episodes.py`, `forecast_labels.py`, `stage1/weak_labeling/` (новая), `ml/forecast/` (новая), скрипты synthetic/evaluation/train/predict |
| Совместное согласование, редактирует один назначенный владелец | `contracts.py`, `observability.py`, общие схемы/конфиги, зависимости, общий README; интегратор A |

Каждый пишет тесты своего кода; независимые тесты B не заменяют тесты A.
Владелец модуля исправляет найденную проблему; второй не меняет тот же файл
параллельно. Общие изменения в наблюдаемости и контрактах проходят ревью обоих.
Новые классы разносить по модулям: не увеличивать бесконечно `detectors.py`
и не собирать всю работу в notebook.

Ветки по задаче: например `codex/a-m2-features`, `codex/b-m2-synthetic`.
Небольшой PR на один проверяемый результат. До merge: тесты, проверка контракта,
команда воспроизведения, размеры/распределения и ограничения. После merge оба
обновляют общую базу. Данные/модели не коммитятся в Git; передаются manifest,
конфигурация и инструкция пересоздания. Финальную оценку держит B после заморозки A;
это разделение настройки и проверки, а не заявка на внешнее независимое исследование.

После каждого M1–M7 — совместная приёмка и подтверждение перехода. Параллельная
разработка B внутри текущего milestone разрешена; скелеты поздних модулей работают
на тестовых контрактах, но реальная псевдоразметка/обучение не обходят gates.

   ему не нужно ждать полного Parquet, достаточно исходников и общей выборки.
