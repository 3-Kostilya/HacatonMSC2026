# ML-план v2: состояния журнала → эпизоды → прогноз
Статус R1: операционный контракт принят для исследовательской цели по
сообщениям журнала; см. [решение R1](ml-r1-operational-accepted.md).
Дата: 2026-09-23. Заменяет прежнюю обязательную цепочку через алгоритмические
псевдометки. Предыдущая версия сохранена в
[архиве](archive/pre-state-dictionary-20260923/ml-two-person-plan.md).
Основание изменений: [аудит справочника](state-dictionary-review.md).

## Постановка и границы

Работаем только с имеющимися файлами. Дополнительных справочников и экспертной
разметки не ждём. В объёме только данные, разметка, модели и их оценка.
A — данные, признаки и их расчёт. B — семантика целевых состояний,
эпизоды, target, обучение и оценка. Опыт сопоставим, исходники доступны обоим.

Предложение «разметить → обучить» верно как направление, но разметка требует
согласованной цели, проверки соответствий и временной структуры.
Новый CSV содержит состояния и признак тревоги, а не подтверждения физического
отказа. При текущем сопоставлении он покрывает кандидатами только 3,78%
текстовых записей; для каналов нет ключа набора состояний, есть противоречия.

Рекомендованная первая цель:
**предсказать новое зарегистрированное начало состояния «Неисправен»
в следующие 24 часа по истории, доступной на момент расчёта.**
Это конкретная проверяемая цель по журналу, не диагноз физического отказа.
Горизонты 6/12/48 часов допускаются отдельными конфигурациями.

Для исследовательской версии цель принята в [контракте R1](ml-r1-operational-accepted.md).
Другие технические состояния (например, неисправность батареи) — отдельные
определения/виды target после проверки. Дым, газ, движение и затопление нельзя
объединять с неисправностью датчика лишь потому, что они тревожные.

Три разные задачи:
- Расшифровать текущее сообщение — детерминированная таблица правил.
- Предсказать будущее целевое сообщение/эпизод — основная ML-задача.
- Найти необычное поведение без целевого сообщения — отдельная исследовательская
  ветка; она не переименовывается в подтверждённый отказ.

контракты, но не массовая разметка/обучение по неутверждённой цели.

## R1. Отделить смысл состояния от alarm и от целевой метки

### A1 — техническая таблица соответствий

Вход: три существующих справочника и чистый Parquet. Сохранить оригинал нового
CSV и хеш, полные дубликаты убрать только из производной таблицы.
Для каждого наблюдаемого сочетания типа/текста сформировать:
кандидатные state_set_id, expected_alarm, observed_alarm, согласованность,
статус сопоставления и provenance.

Статусы: exact_candidate, multiple_candidates, conflicting_definition,
unmapped_state, unmapped_type. Даже exact_candidate не объявляется
подтверждённой связью channel → state_set. Не выбирать кандидат по совпадению
его alarm с наблюдаемым, не исправлять типы по «похожему» названию.
Изменения нормализации текста — только явный список, исходное значение сохраняется.

Выход: state_mapping_audit.parquet + агрегированный отчёт.
Неполный справочник не должен отбрасывать сообщения из исходной истории.

### B1 — семантическая таблица и определение цели

Категории сообщения: normal, operational, environmental_alarm,
technical_fault, unknown. Для каждого правила указать тип/область применимости,
точное состояние, категорию, источник правила, причину и версию.
Alarm хранить отдельно: false не означает исправность, true не означает отказ.

Источники различать:
- dictionary_candidate — информация из нового файла, со статусом сопоставления;
- project_rule — явное определение исследовательской цели по сообщению журнала;
- unresolved — значение пока не интерпретируется.

Без внешних данных допустимо определить цель по точному тексту «Неисправен»:
это факт наличия сообщения в журнале. Но нельзя назвать это подтверждением
физической поломки или утверждать, что новый CSV подтвердил все такие сообщения.
Для неизвестного типа/непроверенной области использовать отдельный статус,
а не назначать семантику наугад.

При необходимости расширить цель техническими состояниями — отдельная версия
target_kind и отчёт по каждой причине. Не смешивать environmental_alarm
с technical_fault ради увеличения количества positive.

Выход: state_label_rules + target_definition с версиями.
В определении target зафиксировать временной горизонт, начавшийся эпизод,
восстановление, повтор, спорную секунду, unknown и достаточность наблюдений.

### Совместная приёмка R1

Проверить все 59 уникальных строк CSV и наиболее частые/целевые состояния
журнала, которых в CSV нет. У каждого правила должна быть трассируемая причина.
Это ревью определения задачи разработчиками, не предметное подтверждение отказов.

Fixtures: противоречивый alarm, «Батарея неисправна» с false, дым с true,
обычный рабочий режим, неизвестное состояние/тип, несколько наборов.
Статус технического сообщения нельзя вычислять просто как int(alarm).
Не начинать массовую разметку до согласования правил и версии цели.

## R2. Признаки и эпизоды строятся одновременно

### A2 — прошлые признаки и пригодность

Переиспользовать текущие окна 1/6/24/168h, счётчики событий и тревог,
числовую статистику, интервалы, частоту состояний и переходы.
Добавить прошлую историю согласованных категорий: число технических сообщений,
время после последнего завершённого эпизода, частоту повторов, длительности,
доступные к моменту t. Не добавлять длительность ещё не завершившегося будущего эпизода.

Разделить пригодность:
- для числового профиля;
- для дискретных признаков;
- для конкретной модели;
- для будущей метки (её вычисляет B).

Отсутствие чисел/MAD не должно автоматически блокировать модель по дискретной
истории. Отсутствие достаточной истории тоже нельзя скрывать формальным статусом
eligible. Проверить причины нулевого eligible в A2-выборке; измерить покрытие
до/после на одинаковых каналах. Недоступные необязательные numeric-признаки
могут оставаться null при пригодной state-ветке.

Сейчас связи с объектами нет: peer/object признаки недоступны. Общая принадлежность
к типу не заменяет реальное соседство. Все типы остаются в аудите; модель для типа
допускается только при достаточных данных.

### B2 — эпизоды зарегистрированного состояния

Вход: сообщения с согласованными правилами R1, не scores кластеризации.
Один эпизод — начало выбранного технического состояния, его повторы и завершение
по определённому правилу восстановления. Не считать каждое сообщение новым отказом.

Для явно зарегистрированного дискретного состояния не обязательно требовать
три сообщения подряд, как у score-детектора: подтверждение определяет R1.
Начало — время первой подходящей записи после подтверждённого выхода из
предыдущего эпизода. Неизвестная предыстория/первая запись уже «Неисправен» —
left-censored, не уверенное новое начало. Это начало регистрации, а не
восстановленное время физической поломки.

Не закрывать эпизод по alarm=false: «Неисправен» встречается и с false.
Не считать молчание восстановлением. Число или другое сообщение считается
восстановлением только по явному применимому правилу; иначе конец unknown.
Сохранить конфликты времени, открытые и сомнительные эпизоды.

B3 score_episodes.py содержит полезные тесты и приёмы учёта времени,
но его пороги/гистерезис нельзя механически использовать для дискретных состояний.

Выход: registered_state_episodes.parquet с episode_id, channel_id, type,
target_kind, start_at, confirmed_at, end_at?, onset_status, evidence и версиями.
Отдельный отчёт: число сообщений и число эпизодов, открытые/сомнительные,
по каналам/типам/годам. Проверить 50 эпизодов с историей до/после плюс
normal/unknown-контроли; если их меньше, проверить все и указать объём.

Реализация и результаты B2: `docs/ml-r2-b-registered-episodes.md`.

## R3. Преобразовать эпизоды в прогнозную задачу

### B3 — target и временные части

Единица: channel × prediction_time. Основной H=24h, признаки только <= t.
- 1: новое уверенно зарегистрированное начало находится в (t,t+H].
- 0: в достаточно наблюдаемом будущем окне такого начала нет, неопределённость
  состояния/пропуски не мешают это проверить.
- unknown: будущее неполно, восстановление/начало спорно, противоречия
  или другие ограничения target_definition.
- excluded: выбранный эпизод уже активен на t, неподдерживаемая операция.

Ноль означает отсутствие выбранного будущего события при условиях задачи,
а не физическую исправность и не отсутствие любых аномалий.
Подтверждённый positive может быть известен при неполном остальном окне;
условия пригодности именно positive фиксируются отдельно от условий negative.
Признаки и наблюдаемость на t всё равно должны быть пригодны.

Для цели «зарегистрированное сообщение» полнота журнала и наблюдаемость
физического состояния — разные предпосылки. Определить, какие интервалы истории
считаем доступными для проверки отсутствия записи. Глобальная дата конца архива
не доказывает полноту конкретного канала; молчание не объявлять нормой.
Если пригодных negative нет, это проблема выборки/постановки, а не повод
заменить unknown нулями. Допущение о полноте выгрузки фиксируется в отчёте.

Зафиксировать train/validation/test до обучения и подбора параметров.
Даты выбрать по фактическим эпизодам/покрытию, показать ограничения малых групп.
У границ убрать примеры, чья целевая зависимость/подтверждение пересекает
следующий период; один эпизод не должен давать зависимые метки по обе стороны.
Прошлые окна validation законно используют события из предшествующего train:
перекрытие прошлой истории само по себе не требует автоматически удалить 7 дней.
Если проверяется строгая независимость эпизодов/каналов — отдельное разделение.

Контролировать число почти одинаковых positive-снимков. Валидацию и тест
не балансировать; веса/выборку отрицательных применять только в train.
QA-выборку 20 каналов не использовать как готовый train/test: она проверяла
структуру и использовала наличие записей в проверяемом периоде.

Контракт B3 и ограниченная проверка разметки: `docs/ml-r3-b-registered-target.md`.
Полная разметка A3 и числа классов по split: `docs/ml-r3-b-full-population.md`.
Окончательный допуск строк к обучению зависит от совместного решения A и B
по наблюдаемости каналов; полный пакет меток сам по себе его не устанавливает.

### A3 — передаваемый набор признаков

Передать версионированный feature pack, список разрешённых полей, статусы,
временные границы и команды расчёта. Сырые ID событий, episode_id, split,
будущие сообщения, причина целевого исхода и provenance не являются признаками.
Прошлые alarm/состояния допустимы, если они известны на t и target находится
в будущем; запрещать всю историю состояний не нужно.

Приёмка: количество 0/1/unknown/excluded, независимых эпизодов, каналов и
наблюдаемых дней по каждому split/типу; случаи без обоих классов явно указаны.
Добавление будущих данных не меняет признаки в t; граничные примеры проверены.

## R4. Получить честный supervised-baseline

B обучает на одном и том же наборе:
1. Простые правила: прошлые технические сообщения/повторы и частота эпизодов.
2. Logistic Regression.
3. CatBoost.

Отдельные модели по совместимым группам или общая модель с типом — сравниваемые
варианты, решение зависит от объёма и метрик по типам. Не требуется модель
для типа с недостаточными метками. Текущий текст целевого сообщения не поступает
на вход для «прогноза» той же строки: это было бы восстановление словаря.

A параллельно завершает вычисление признаков по временным частям, проверяет
одинаковый результат batch/replay и расход памяти. Не перечитывать 259 млн
строк для каждого эксперимента — сохранять пригодные промежуточные таблицы.

Приёмка: метрики validation на зафиксированном target, сравнение с простыми
правилами, разбор утечки при подозрительно высоком качестве. Старый
smoke_failure target похож на узкую новую цель, но его старые метрики
не считаются результатами новой разметки и всех типов.

## R5. Кластеризация и IF — проверяемое улучшение

A: статистические deviation/change point, IsolationForest, MiniBatchKMeans,
HDBSCAN и переходы режимов по совместимым типам. Учить на разрешённом прошлом,
ограничивать вклад очень частых каналов, масштабировать без всей истории в RAM.
Для новых окон нужен определённый способ оценки без обучения на будущем.

B: сравнить rolling+state baseline; +stat; +IF; +clusters/transitions;
+change point; полную комбинацию на одинаковом target, split и покрытии.
Метка зарегистрированного состояния при добавлении кластера не изменяется.
Если группа недоступна для сложного метода, показать покрытие и сравнение
на общей области, не получать улучшение простым исключением трудных примеров.

Scaler/imputer/unsupervised-модели fit только на разрешённой train-истории;
для train-признаков использовать ранний fit-период или временные OOF оценки.
Номер кластера не имеет порядкового смысла; версии режимов различаются при переобучении.

Синтетика B2 остаётся полезной для причинности, дрейфа, пропусков и устойчивости.
Она не заменяет real temporal test прогноза зарегистрированного состояния
и не обязана быть источником основной разметки.
Алгоритмические псевдоэпизоды не добавлять молча к supervised target.
Это отдельный эксперимент с собственным label_source, метриками и названием.

## R6. Итоговая оценка и inference

B: выбирать порог/калибровку только на разрешённой validation-части.
После фиксации решения — один финальный test. Если прошлые годы уже многократно
просматривались в других экспериментах, отметить это; переименование старого
отрезка не делает его новым holdout. Возможную свежую часть определить по
журналу экспериментов до настройки.

Метрики: PR-AUC по снимкам, Precision/Recall по предупреждениям/эпизодам,
ложные предупреждения на наблюдаемый канало-день, lead time, coverage/unknown,
числа каналов/эпизодов, метрики по типам. Не считать сообщения независимыми
случаями отказа. Один эпизод — один TP, повторные уведомления — отдельная нагрузка.
На цель H=24h не заявлять упреждение >24h без отдельного эксперимента H=48h.
Показать feature importance/SHAP на ограниченной выборке и смысл прогноза.

A: единый причинный путь история → признаки; B: признаки → модель → таблица
прогнозов. Пакет: модель, preprocessing, правила состояний/эпизодов, горизонты,
порог, feature/target/dictionary versions, eligibility и временной протокол.
Inference не переобучает модель и не читает все архивы заново.

Вероятность относится к зарегистрированному целевому эпизоду и заявленной
популяции, не к физической поломке. При слабой калибровке выдавать score
с ограничениями. Отсутствие оценки не превращать в нулевой риск.
Качество CatBoost может оказаться хуже простого правила — это результат проверки.
