# M0 — результат технической проверки B

Дата: 2026-09-22. В этой рабочей копии пользователь — **B**, друг — **A**.
Исходная общая база: `3e5b09bff4c6c24ef3660ab8fa62755c10b94556`.
При начале проверки рабочее дерево было чистым; ingestion, контракты и fixture
уже входили в этот коммит. Старые утверждения об untracked-файлах устарели.

**Статус:** техническая часть M0 со стороны B выполнена. Изменения текущей
проверки пока в рабочем дереве. Совместная приёмка A+B не заявляется: нет
подтверждения A о воспроизведении этой версии и принятии критериев ниже.

## Проверенные результаты

- Общий набор: 32 входные строки, 31 принята, 1 exact duplicate; 1 неизвестный
  канал, 2 конфликтующие строки, numeric/state/mixed и промежуток без сообщений.
- Синтетический numeric-канал даёт два раздельных эпизода. Объектная связь
  отсутствует явно; новый канал проверяется как недоступный прогноз.
- Шесть публичных схем `ml-m0-v1`, nullable target, ключи, типы и временные
  границы проверены. Проверены SHA-256 четырёх fixture-файлов после нормализации
  CRLF → LF, чтобы Windows/Linux читали одинаковое логическое содержимое.
- Усилена проверка уже описанных правил: unavailable требует причины,
  probability/risk отсутствуют при недоступном прогнозе; NaN/Inf запрещены,
  probability ограничена [0,1], доступное расстояние требует значения и меры.
  Временные функции отклоняют timezone-aware значения.
- 136 тестов stage1 прошли, включая 17 проверок M0 и прогнозной метки.
  `ruff check .` и `ruff format --check .` прошли.

Публичные поля не менялись; это исправление валидации существующего контракта,
поэтому версия схемы сохранена. Общий модуль контрактов требует ревью A.
Тест с двумя читателями выполняется локально и не доказывает запуск на машине A.

## Предлагаемые критерии B до настройки

Это исходные исследовательские бюджеты, а не требования заказчика и не
измеренное качество. После согласования A+B они фиксируются до tuning;
изменение требует новой версии протокола и нового непросмотренного holdout.
Оценка проводится отдельно для каждого семейства **и применимого вида аномалии**.

| Семейства реестра | FP / наблюдаемый канало-день, не более | Задержка подтверждения p90, часов, не более | Покрытие пригодных окон, не менее | Episode Recall, не менее |
|---|---:|---:|---:|---:|
| numeric_environment | 0,01 | 6 | 0,90 | 0,80 |
| power_mixed | 0,01 | 6 | 0,90 | 0,80 |
| equipment_state, power_state | 0,01 | 3 | 0,90 | 0,80 |
| fire_discrete, flood_discrete | 0,005 | 2 | 0,95 | 0,90 |
| security_contact, security_mode | 0,01 | 3 | 0,90 | 0,80 |
| control_event, manual_event, security_event | 0,01 | 3 | 0,90 | 0,80 |
| hardware_state_unknown_role, security_contact_unknown_subtype, security_multi_section_unknown | N/A до подтверждения семантики | N/A | N/A | N/A |

Обоснование: 0,01 соответствует в среднем одному ложному эпизоду на 100
наблюдаемых канало-дней; для fire/flood бюджет вдвое строже. Это проверка
устойчивых аномалий журнала, не нормативное время реакции пожарной системы.
Часовая сетка допускает 2–3 наблюдения для дискретного подтверждения и 6 часов
для устойчивого числового изменения. В numeric/power_mixed плавный drift
оценивается отдельно с p90 ≤ 24h и длительностью воздействия ≥ 48h; остальные
устойчивые воздействия для шестичасового критерия длятся ≥ 12h.
Для дискретных тестов длительность устойчивого воздействия ≥ 6h.
Амплитуды и скорость drift стратифицируются в B2 и фиксируются до tuning:
эти минимальные длительности не разрешают исключать трудные случаи из отчёта.

Для событийных каналов применимы аномалии частоты/переключений; одиночное
штатное событие и молчание не являются отказом. Dropout оценивается только
при известной периодичности. Numeric/state ветви mixed оцениваются раздельно.
Для неизвестной семантики правильный результат — unknown с причиной;
проверка сохранения данных обязательна для всех 19 типов.

Покрытие = окна с доступным результатом / все окна заранее объявленной
пригодной популяции после прогрева; исключения и доля unknown публикуются
отдельно по всей популяции, чтобы нельзя было улучшить метрики её сокращением.
FP считаются только на фоне с известной истиной; реальные фрагменты без истины
дают нагрузку кандидатами, не FP. Один truth-эпизод даёт максимум один TP,
повторное уведомление не повышает Recall. Вид воздействия оценивается отдельно.

На каждую применимую пару семейство/воздействие в закрытом наборе требуется
не менее 50 truth-эпизодов и 1000 наблюдаемых отрицательных канало-дней на
семейство, не менее 10 независимых каналов/фоновых реализаций. Отрицательный
фон покрывает шум, сезонность, штатные циклы, spike, общую смену среды и
пробел выгрузки. При недостатке объёма — `insufficient_evidence`, не допуск.
Публикуются интервалы неопределённости с группировкой по независимому фону;
точечное выполнение бюджета не означает доказанной эксплуатационной надёжности.

## Разделение данных и защита закрытой оценки

Протокол времени из `ml-m0-owner-b-protocol.md` сохраняется. Даты нельзя
выдумывать до аудита полного покрытия M1. До обучения B фиксирует календарные
границы, максимальное время подтверждения, fit-период либо хронологические
фолды. Для каждого снимка зависимость охватывает `(t-168h, label_verified_at]`;
при отрицательной цели также нужно время, достаточное для подтверждения
отсутствия начал у правой границы. Пересекающие границу split зависимости
исключаются. Одна константа purge без проверки этих интервалов недостаточна.

В B2 создаются отдельные манифесты tuning и holdout: `background_id`,
`source_channel_id`, `source_interval`, `parent_background_id`, `scenario_id`,
`episode_id`, параметры воздействия, seed и хеш содержимого. Между наборами
не допускаются одинаковые каналы/фоновые реализации, пересекающиеся исходные
отрезки и производные одного фона. Одной смены seed недостаточно.
Эталонные поля и параметры воздействия не передаются моделям. Фиксированный
M0 fixture публичен и никогда не становится закрытым holdout.

Прогнозные ориентиры Precision > 0,7 и Recall > 0,5 проверяются на естественной
частоте событий; это цели, а не условие, которое можно обеспечить изменением
псевдометки. Обучение прогноза остаётся задачей M6 после допуска разметчика.

## Воспроизведение и передача A

Из корня проекта, Python 3.14:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install pyarrow==25.0.1 duckdb==1.5.5 ruff==0.14.14
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s stage1 -p "test_*.py" -v
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Это минимальное окружение M0, не полный набор зависимостей обучения.
Общая база зафиксирована выше; для передачи дополнений нужен общий коммит
после ревью. Файлы fixture не менялись. Данные и модели не добавлялись в Git.

| Решение | Состояние |
|---|---|
| B воспроизвёл общий fixture и проверил контракты | Выполнено в этой рабочей копии |
| Критерии и порядок split/holdout подготовлены до настройки | Выполнено, критерии предложены для согласования |
| A принял изменения общего контракта и критерии, воспроизвёл тесты | Ожидается |
