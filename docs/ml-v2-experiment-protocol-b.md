# ML v2 / B — протокол улучшения прогноза зарегистрированного события

Дата: 26.09.2026. **Статус: протокол B; требуется совместная сверка с A.**
Цели задания `Precision > 0,7` и `Recall > 0,5` оцениваем на уровне
**предупреждение ↔ новый зарегистрированный эпизод**; эту единицу измерения
подтвердил пользователь. Пользователь также подтвердил полный знаменатель
Recall, чтобы отсутствие прогноза не скрывало пропуски. A должен сверить
совместимость этого определения со своим новым допуском и источниками.
Замороженный R6 остаётся неизменной исторической базой; прежний test уже
просмотрен и **не участвует** в обучении, выборе признаков, модели или порога
v2. Требования подтверждаются только позднее на новых независимых данных.
Живой пилот — отдельная задача.

## Цель, время и популяция

Предсказываем новое начало зарегистрированного сообщения «Неисправен» в
журнале за горизонт `(t, t+24h]`, а не доказанную физическую поломку датчика.
Первое неопределённое начало, открытый эпизод, `unknown` и `excluded`
сохраняют прежнюю семантику; отсутствие строки не становится отрицательной
меткой. Предположение о полноте архива остаётся операционным ограничением.

Разбиение R3 оставляем по времени: прежние train-периоды до 2025 года без
специально исключённого года, validation — январь–декабрь 2025 года. Ранее
открытый test не читать для v2. Соседние горизонты очищаются прежним purge;
история до `t` может переходить через границу train/validation только как
причинная предыстория, не как целевая метка. Новые признаки A должны иметь
время доступности не позже `t`; все fit-операции, включая кодирование,
импутацию и калибровку, проводятся только на train. Для внутренних
гиперпараметров используем временные train-фолды, а validation — для
заранее перечисленных моделей и одного выбора порога.

**Основной знаменатель Recall:** все новые положительные
эпизоды с назначенной меткой в validation-популяции, включая эпизоды,
которые текущий допуск не позволил оценить. На закреплённом R3 это **2 142**
эпизода. Прогноз для недопущенного часа не выдаётся и не считается TP.
Второй показатель — условный Recall только по эпизодам, имеющим хотя бы
один допустимый для модели час. При прежнем допуске таких **261**.
Отдельно считаем долю оценённых канал-часов, доступных эпизодов и причины
`unknown`/`excluded`; расширение допуска не выдаём за улучшение ранжирования.

Если A изменит правило допуска, потребуется новая версия популяции,
ключевой аудит A/B и пересчёт **всех** моделей на одинаковом новом наборе.
Для отделения эффекта признаков от охвата нужны два среза: общие часы старого
и нового допуска, затем вся новая допустимая область с недоступными часами
в полном знаменателе. Зафиксированный R6 сравниваем в его исходной области;
его формулу на расширенном допуске можно показать лишь как **новый
диагностический вариант**, не переименовывая его в прежний R6.

## Метрики и правило предупреждений

При пороге одно предупреждение выдаётся на канале, если score его достиг.
Повтор в течение 24 часов после выданного предупреждения подавляется,
в том числе если первое предупреждение не сопоставилось с эпизодом.
Первое предупреждение на канале в `[начало−24h, начало)` сопоставляется
с этим новым эпизодом один раз. Позднейшие предупреждения по уже
сопоставленному эпизоду считаются несопоставленными. Предупреждения без
подходящего эпизода тоже несопоставлены. Сопоставление делаем по тому же
ключу эпизода и `label_available_at`, что в R4–R6.

- `Precision = число сопоставленных эпизодов / число выданных предупреждений`.
  При нуле предупреждений цель не выполнена.
- **Основной** `Recall = число сопоставленных эпизодов / число
  всех назначенных положительных эпизодов`; условный Recall публикуется рядом.
- Строгие цели: **больше** 0,7 и **больше** 0,5 одновременно, не `≥`.
  F1, часовой PR-AUC и число лишних предупреждений — дополнительные метрики.
- Публикуем TP, все предупреждения, несопоставленные и подавленные повторы,
  медианное/квантильное упреждение, полное и условное покрытие, нагрузку на
  1000 канал-дней. Исследовательские 2 несопоставленных предупреждения на
  1000 канал-дней не являются утверждённым эксплуатационным лимитом.

Один общий порог — основной эксперимент. По каждому типу показываем число
назначенных и доступных эпизодов, предупреждений, TP, Precision/Recall,
охват, неизвестные/исключённые часы и нагрузку. Типы без положительных
эпизодов получают неопределённый Recall, а не ноль; редкие типы не
исчезают из таблицы. Раздельные пороги по типам можно изучать только
отдельной версией при достаточной поддержке и заранее заданном правиле,
иначе validation легко переобучить. Отдельно показываем месячную
устойчивость и интервалы неопределённости по каналам/эпизодам.

## Эксперимент и выбор

Для передачи A нужны помесячные train/validation-признаки с ключом
`channel_id, prediction_time`, типом, версией списка полей, временем
доступности каждого нового источника и манифестом SHA-256. Метки и будущие
эпизоды в файлы признаков не входят. Допуск передаётся отдельно как
`eligible/unknown/excluded` с причиной для каждого ожидаемого канал-часа;
изменение допуска сопровождается отчётом по ключам и положительным эпизодам
в целом и по типам. B сверяет этот пакет с закреплённой разметкой R3 и
строит одинаковые обучающие/оценочные строки для всех кандидатов.

На неизменной общей validation-популяции сравниваем замороженное правило
R6, прежние Logistic Regression и CatBoost на 51 утверждённом признаке,
а после проверки A — CatBoost и простой линейный контроль с новыми
причинными признаками. Исторический R5 сохраняем для контекста, но
сравниваем только его принятый полный пакет. Train-выборка и веса
документируются; естественную частоту классов validation не балансируем.
Гиперпараметры и обработку пропусков фиксируем по внутренним временным
train-фолдам до основного validation-сравнения. Сохраняем хеши источников,
список признаков, версии кода, модель, все validation-баллы и полную кривую.

Сетку порогов фиксируем до чтения validation-меток: все различные значения
небольшого дискретного правила и детерминированные квантили непрерывных
баллов, с уточнением около лучших кандидатов по заранее записанному
алгоритму. У каждого варианта одна и та же процедура. Если найден порог,
удовлетворяющий обеим строгим целям на validation, выбираем наибольший
основной Recall, затем большую Precision, меньше предупреждений и более
высокий порог. Если порога нет, **требования не достигнуты**; для изучения
можно отметить максимум F1 по основным Precision/Recall на validation,
не называя его готовым решением.
Это правило выбора реализовано в `ml/forecast/v2_threshold.py`; оно
возвращает пустой выбранный порог, если ни один кандидат не прошёл обе цели.
После выбора фиксируем версию, артефакты и порог; новая независимая оценка
проводится отдельно, без повторной подстройки по ней.

## Проверенный старт и препятствие охвата

`analysis/audit_v2_validation_start.py` сверил хеши принятых R4/R5
validation-кривых и полного R3-отчёта, не открывая test. На прежнем
допуске — 1 365 077 validation-часов, 261 доступный положительный эпизод
из 2 142 назначенных. Даже при обнаружении всех 261 максимальный основной
Recall составил бы **12,18%**. На сохранённых сетках порогов 3 моделей R4
и 7 вариантов принятого R5 ни один порог не удовлетворяет обеим целям;
сетки не доказывают глобальный оптимум по всем возможным порогам.
Для ориентира замороженное правило на validation при пороге 7,1 имело
78 сопоставленных эпизодов из 255 предупреждений: условные Precision
**30,6%**, Recall **29,9%**, основной Recall **3,64%** от 2 142.
Этот старт не является новым обучением и не заменяет будущий эксперимент
с признаками и допуском A.

Ограничение сильно различается по типам: у дымовых датчиков доступно
118 из 1 118 назначенных эпизодов (10,6%), у «Состояния фазы» — 116 из
335 (34,6%), у температурных датчиков — 1 из 408 (0,25%), у ручных
извещателей — 1 из 142 (0,7%). Все типы, включая редкие и с нулём
доступных эпизодов, перечислены в машинном отчёте
`output/ml-v2-validation-start-v4-20260926/report.json` (SHA-256
`66089fc60158468d2859d396e9a6b71c50a5aea76d8d938529a39d43a689e513`).
Новые признаки A должны улучшать качество **на сопоставимой области**, а
новое правило допуска — расширять её без потери причинности и надёжности
меток; оба эффекта в отчёте разделяются.

До получения новых независимых данных нельзя утверждать достижение
порогов задания. Предыдущий закрытый test остаётся только историческим
результатом R6. Ветка разработки — `ML`; большие пакеты хранятся в
игнорируемом Git `output/`.
