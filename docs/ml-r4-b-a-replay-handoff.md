# Передача A для независимой проверки R4

В ветке `ML` находится код и решение B. Пакет результатов B не входит в Git:
`output/r4-a-replay-handoff-20260925.zip` (29 740 928 байт,
SHA-256 `3099751e1ec262ded4434ba82cb27453034724c9e33f2b0d5dbd5ecc41e16069`).
Внутри семь корневых каталогов: B2, индекс допуска R3, модели R4,
validation-аудит, кривые порогов, устойчивость и проверка 50 трасс по M1.
Всего 199 элементов ZIP. До передачи A файл остаётся локально у B.

На машине A распаковать архив в `output/` репозитория, сохранив
имена корневых каталогов. Пакеты A3 и B3 у A уже есть и сверены по
исходным хешам; для повторения проверки исходных 50 трасс нужен также
очищенный M1. Отсутствующие пакеты не заменять файлами из Git.
Команды повторного расчёта приведены в
[итоговом ревью B](ml-r4-b-final-review.md). Исправленная проверка
входов принимает LF и CRLF для двух версионированных текстовых файлов
R3, но продолжает сравнивать байты данных, моделей и манифестов.

Кандидат B для проверки A: простое правило, порог 7,1 при 24-часовом
подавлении повторов. Критерий: максимум найденных эпизодов среди
порогов с не более чем 2 лишними предупреждениями на 1000 канал-дней,
при равенстве — меньше лишних предупреждений. Это исследовательский
бюджет validation, а не согласованное требование эксплуатации.
В первом часовом сравнении использовался порог 6,6; максимум
эпизодного F1 без ограничения нагрузки достигается при 6,1.
Окончательный порог, закрытый test и совместная приёмка R4 ожидают
batch/replay и ресурсную проверку A, затем согласование в R6.
