# Проверка нового справочника состояний

Дата: 2026-09-23. Это аудит данных для изменения плана, не готовая разметка.
Работаем только с текущими файлами; получение уточнений и дополнительных
справочников не является зависимостью плана.

## Вывод

Справочник полезен для расшифровки части сообщений и проверки согласованности,
но его текущая версия не является достоверной бинарной разметкой отказов.
Прямой join с последующим `target = тревожное` даст неоднозначную и неполную цель.
Из него нельзя автоматически восстановить связь канала с набором состояний.

Основной путь можно упростить до обучения на зарегистрированных технических
состояниях, если явно определить эту цель и утвердить воспроизводимые правила.
Кластеризация/IF для такой цели не обязаны предварительно создавать псевдометки.
Прогноз зарегистрированного сообщения и прогноз физического отказа — разные утверждения.

- `data/справочник_каналов_датчиков.csv`: канал, система, тип, тег, название.
  Поля `ид_набор_состояний` и `ид_объект` отсутствуют.
- Все 79 чистых месячных разделов `output/milestone1/full_20260922/clean/`:
  259 453 121 запись. По опубликованному отчёту полного ingestion исходных строк
  260 017 062, точных дубликатов 563 940, повторный заголовок — 1.
- Отчёт диагностики совпадений: `output/state_dictionary_review_20260923/audit.json`.
  Он содержит агрегаты по году, типу, исходному тексту и фактическому alarm.

Чистую историю прочитали через DuckDB, в Python переданы только агрегаты.
Базовый запрос: группировка `year, sensor_type, value_state, alarm` с `count(*)`
из полного набора Parquet. Для каждого текстового агрегата искались кандидаты
по равенству `sensor_type` и `value_state.strip()` полям типа и названия в CSV.
Регистр/синонимы/числовые пороги/ошибки текста не исправлялись.
Это диагностическое сопоставление, а не установленная принадлежность набору.
Флаг alarm не использовался для выбора кандидата; его согласованность проверена после join.

## Структура и конкретные проблемы

В файле 62 строки, 59 уникальных полных строк, 17 наборов состояний и 10 типов
из 19 типов справочника каналов. Нет дат действия/версий наборов и связи с каналами.

1. **Противоречие внутри ключа.** Строки CSV 54, 55 и 58:
   `Газовый датчик / 13 / Температура ниже 3ºC1` имеет одновременно `false` и `true`.
   Нельзя выбрать первую строку, большинство или значение, совпавшее с alarm журнала.
   Последнее искусственно скроет конфликт за использованием самого ответа.
2. **Несоответствие типов требует проверки.** `Обнаружен дым` находится под
   `КД АВ` (строка 12), а у `Датчик дыма` перечислены рычаги и питание (28, 38–44).
   Температурные диапазоны перечислены у газового датчика. В журнале у дымовых
   датчиков есть `Обнаружен дым`: 152 540 записей, для пары с этим типом соответствия нет.
   Причина не установлена: это может быть ошибка связи, иной смысл типов или версия
   конфигурации. Автоматически переставлять названия типов нельзя.
3. **Тревога не равна технической неисправности.** `Батарея неисправна` помечена
   `false` (42), `Обнаружен дым` — `true` (12). Первое техническое сообщение нельзя
   объявлять нормой по false; второе не доказывает поломку дымового датчика.
4. **Набор нельзя назначить каналу.** Даже уникальное совпадение названия в текущем
   CSV не доказывает, что именно этот набор был настроен на канале в соответствующем году.
   Для `КД Дверь / Норма` есть два набора с одинаковым alarm: значение флага
   совпадает, но идентификатор набора всё равно не установлен.
5. **Нет полной интерпретации числовых значений.** Названия отдельных температурных
   диапазонов не задают единицы и пороги для каждого исторического канала.
   Нельзя объявлять любое число нормой или применять текстовый порог ко всем газам.

Отсутствующие типы: 9-секционный люк, Датчик затопления, ИБП, Переключатель,
Ручной извещатель, Состояние УИР-Р, Состояние охраны, Стекло, Тепловой датчик.

| Категория | Число записей |
|---|---:|
| Числовые значения без текстового состояния | 188 715 520 |
| Текстовые записи: тип отсутствует в CSV, включая неизвестный тип | 12 985 218 |
| Текстовые записи: тип есть, название состояния для него отсутствует | 55 078 125 |
| Совпадение типа/текста с единственным набором-кандидатом | 615 379 |
| Совпадение типа/текста с несколькими наборами и одинаковым alarm | 2 058 879 |
| Итого | 259 453 121 |

Всего текстовых записей: **70 737 601**. Кандидатные совпадения:
**2 674 258, или 3,7805% текстовых и 1,0307% всех записей**.
Это верхняя оценка покрытия текущим сопоставлением, не доля надёжной разметки.
У 384 совпавших записей alarm журнала расходится с единственным значением alarm
кандидатов CSV; у 2 673 874 совпадает. Совпадение флага не подтверждает физическую
норму/поломку и не доказывает правильность типа или набора.

Конфликтующий ключ температурного состояния в этой истории не встретился;
это не снимает противоречие в справочнике для следующих выгрузок.

В журнале **414 299 сообщений с точным текстом `Неисправен`**, в том числе
127 857 у дымовых каналов и 9 187 у неизвестных каналов. Это сообщения,
не независимые эпизоды и не 414 299 подтверждённых физических отказов.
В новом CSV `Неисправен` есть только для `КД Дверь`; у дымовых датчиков такое
сообщение новой таблицей не покрывается. Следовательно, полезную узкую цель
«будущее зарегистрированное Неисправен» можно определить по журналу, но нельзя
утверждать, что новый справочник подтвердил её для всех типов.

## Ограничение уже подготовленных признаков

Существующий результат `output/milestone2/a2-real20-june2025/` содержит
14 400 часовых строк / 20 каналов. В `validation_report.json`:
13 680 `unknown`, 720 `excluded`, 0 `eligible`; 13 171 строка без numeric за 24h.
Это ограниченная QA-выборка, не репрезентативная оценка пригодности всей истории;
отбор использует наличие записей в проверяемом периоде и не является train/test split.

Нужен отдельный аудит причин пригодности для числового профиля, дискретных
признаков и будущей целевой метки. Нельзя автоматически объявлять все строки
eligible или, наоборот, исключить все state-каналы только из-за отсутствия
numeric baseline. Изменения критериев должны иметь предметный смысл и тесты.

## Решение для нового плана

1. Зафиксировать исходный CSV как есть; очистить полные дубликаты только в
   производной таблице, противоречия сохранить как флаги.
2. Отдельно хранить `dictionary_match_status` и семантическую категорию сообщения.
   Отсутствие строки в справочнике не запрещает узкую цель по явно заданному тексту,
   но источник такого правила — `project_rule`, а не `dictionary_confirmed`.
3. Ввести категории normal, operational, environmental_alarm, technical_fault,
   unknown. Это не готовый бинарный target будущего.
4. Основная рекомендованная первая цель: новое зарегистрированное начало
   состояния `Неисправен` за 24 часа. Иные технические состояния добавлять
   отдельной версией определения/вида target, после проверки смысла и покрытия.
5. Из повторных сообщений построить эпизоды с проверкой предыстории и восстановления;
   затем получить прогнозный 0/1/unknown и обучать baseline/CatBoost по прошлым признакам.
6. Кластеризация и IF — необязательные дополнительные признаки с ablation,
   а не условие начала supervised-ветки и не источник её тестовой истины.
