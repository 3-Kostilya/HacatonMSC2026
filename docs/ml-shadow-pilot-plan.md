# Отдельный этап: теневой пилот зарегистрированного «Неисправен»

**Статус:** план и контракт B подготовлены после технического закрытия R6.
Теперь подготовлен и [первый технический пакет A](ml-shadow-pilot-a-replay-review.md):
20 каналов, 3 360 ожидаемых часов, 111 доступных прогнозов. Все решения
record-only обработчика B совпали с контролем A. Это ограниченный replay;
совместный допуск, checkpoint состояния A и настоящий пилот ещё не приняты.
[Ревью B](ml-shadow-pilot-b-review.md) приняло причинный допуск A только для
этой исторической проверки и закрепило критерии P2/P3; живой допуск,
доставка событий и эксплуатационная нагрузка остаются открытыми.
[Операционный отчёт B](ml-shadow-pilot-b-operational-review.md) добавил вторую
архивную неделю, разбивку охвата и причин по типам, замеры ресурсов и
контролируемую проверку предупреждения с cooldown. Для согласования будущего
запуска подготовлены [вопросы заказчику](ml-shadow-pilot-customer-questions.md).
Новый checkpoint A и сквозной restart ещё требуют независимой проверки B.
Подробности A вынесены в [дополняющий протокол](ml-shadow-pilot-a-implementation-plan.md).
Это новый этап, а не переоценка закрытого test. Цель — проверить, можно ли
последовательно выдавать объяснимый прогноз из доступной на момент часа
истории, сохраняя причину отсутствия прогноза. Система только записывает
теневые предупреждения: уведомлений заказчику, заявок и автоматических
действий нет. Замороженные правило, коэффициенты, порог **7,1**, горизонт
24 часа и 24-часовое подавление повторов не меняются.

## Границы и последовательность

1. **Контракт входа.** A определяет допуск по прошлым данным и для каждого
   запланированного канал-часа выдаёт `eligible`, `unknown` или `excluded`
   с причиной, а также четыре входа правила и последние моменты истории,
   использованной для признаков и допуска. Ретроспективный индекс R3,
   опирающийся на будущую пригодность метки, в живой допуск не переносится.
   B проверяет контракт и фиксирует формат решения и предупреждения.
2. **Технический replay на имеющихся файлах.** A проводит сообщения по
   времени, сохраняя состояние канала, признаки и допуск без чтения будущих
   событий. B применяет неизменное правило и теневую политику; вместе
   сравниваем пакетный, последовательный и возобновлённый после checkpoint
   расчёт, причины отсутствия, границы месяцев, время и память. Это
   проверка причинности и работы программы, **не новая независимая метрика
   качества модели**. Если в архиве нет реального времени поступления
   сообщений, replay не доказывает задержку доставки.
3. **Свежий теневой запуск.** После согласования интерфейса и источника
   новых сообщений фиксируем период и перечень каналов до появления
   будущих исходов. Для каждого ожидаемого часа сохраняем решение и
   причину отсутствия. Метрики качества считаем только после созревания
   новых меток и отдельного аудита полноты журнала; старый test повторно
   для настройки не используем.
4. **Решение по пилоту.** Совместно сверяем охват, задержки, ресурсы,
   корректность предупреждений и нагрузку по типам. Заказчик отдельно
   определяет допустимую операционную нагрузку и действие оператора.
   Переход к видимым уведомлениям или внедрению требует нового решения.

## Контракт B для одного канал-часа

`ml/forecast/shadow_pilot.py` принимает `channel_id`, `sensor_type`,
`prediction_time` (целый местный час), `admission_status`,
`admission_reason`, `history_through`, `admission_through` и четыре поля
замороженного правила: `registered_fault_text_count_24h`,
`registered_fault_text_count_168h`, `completed_episode_count_168h`,
`technical_message_count_24h`. Оба времени доказательной истории должны
быть не позже часа прогноза. Будущие метки, ID будущего эпизода и split
на вход запрещены. A отвечает за доказательство, что эти отметки и
источники действительно построены только из уже доступных сообщений.

Для `unknown`/`excluded` причина обязательна; score отсутствует.
При `eligible` без отметок происхождения, с будущей отметкой либо
пропущенным/некорректным счётчиком B тоже воздерживается от прогноза и
записывает причину. Это защитное правило теневого интерфейса; оно не
изменяет ретроспективный результат R6. Пустая история сама по себе
не доказывает, что канал пригоден: решение о допуске принадлежит A.

При полном допустимом входе B считает прежнюю сумму четырёх слагаемых.
Порог 7,1 создаёт кандидата предупреждения; повтор по тому же каналу
в следующие 24 часа подавляется, причём состояние сохраняется между
месяцами и запусками. В журнале решения остаются балл, вклад каждого
слагаемого, статус, причина подавления и признак `record_only`.
Повторные сообщения не объединяются с физическими поломками.

## Что измерять и когда принимать

**Наблюдаемые сразу:** ожидаемые канал-часы по заранее заданному перечню,
фактически полученные решения, доля часов с баллом, причины отсутствия,
общие и по типам счётчики записанных предупреждений, подавления повторов,
предупреждения на 1000 наблюдавшихся и на 1000 оценённых канал-дней,
задержка расчёта, пик памяти, число поздних/повторных сообщений. Охват
нового запуска измеряем заново; ретроспективные **9,38%** не переносим.
Для полного охвата знаменатель ожидаемых часов передаёт A из перечня
каналов и расписания; число только обработанных строк недостаточно.

**Техническая приёмка:** ноль чтений будущих событий и целевых меток во
входе, одно решение либо явная причина для каждого ожидаемого часа,
точное совпадение баллов и предупреждений batch/replay/checkpoint,
сохранение 24-часового cooldown через границы частей, воспроизводимые
версии и хеши, измеренные время/память. Порогов SLA пока нет — числа
фиксируются до решения о внедрении. При сбое происхождения или входа
прогноз не выдаётся, а не считается нулевым риском.

**После новых исходов:** отдельно оцениваем обнаруженные эпизоды,
несопоставленные предупреждения и упреждение с задержанной разметкой.
В реальном времени «ложное» предупреждение определить нельзя. Исходный
исследовательский ориентир **2 несопоставленных предупреждения на 1000
канал-дней** нельзя подменять лимитом всех сообщений в живом потоке;
заказчик должен согласовать общий и типовые бюджеты и реакцию человека.

Прогноз относится к будущей записи «Неисправен» в журнале при условном
предположении о полноте архива. Доказательства физической поломки или
непрерывной работы канала из него не следует. Графики обслуживания пока
остаются отдельным источником: подтверждённой привязки к каналам нет.

**Роли:** A — причинный допуск, поток и признаки; B — решение score,
теневой журнал предупреждений, причины и операционные метрики; вместе —
сквозной replay, ограничения и решение о пилоте. Код и контракты идут в
`ML`, большие события, решения и отчёты — в исключённый из Git `output/`.

Пакетный вход B — один Parquet с перечисленными полями, упорядоченный
по времени внутри каждого канала. `analysis/run_shadow_pilot_b.py` читает
его частями, запрещает поля будущей разметки, записывает
`shadow_decisions.parquet`, `checkpoint.json`, `report.json` и манифест.
Следующая часть может продолжить cooldown из предыдущего checkpoint.
Отчёт считает только наблюдаемую нагрузку и причины отсутствия, без
ложноположительных метрик. Пример технического запуска после передачи
пакета A (новые имена выходных каталогов для каждого запуска):

```powershell
.\.venv\Scripts\python.exe -B -m analysis.run_shadow_pilot_b `
  --input output/shadow-a-past-only/hours.parquet `
  --output-dir output/shadow-b-record-only
```

Для полного показателя охвата дополнительно передать
`--expected-channel-hours` из заранее зафиксированного перечня каналов
и часов A; без него отчёт покажет только охват среди поступивших строк.
Первый пакет A с новым допуском: `output/shadow-a-replay-20260926-v3/hours.parquet`.
При передаче нужен весь каталог с манифестом и отчётом; output вне Git.
B должен ревьюить происхождение и допуск, не подменяя их R3-индексом.
