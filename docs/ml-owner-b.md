# Участник B: проверка, псевдометки и прогноз

Это твоё задание (участник B); друг выполняет роль A. Используй его вместе с репозиторием и
[общим планом](ml-two-person-plan.md). Вы делаете только данные и ML:
интерфейс, API и заявки не входят.

Участник A готовит данные, признаки и детекторы/кластеры. Твоя задача —
проверять эти методы, формировать определённую слабую цель и предсказывать
её будущее начало. Для старта не нужно ждать готовой модели или полного Parquet.

## Первое задание

1. Получи согласованную общую Git-ревизию, окружение и исходные архивы.
2. Вместе с A зафиксируй M0: схемы, временные границы, маленький общий набор,
   определения eligible/unknown, план временной проверки.
3. Проверь данные независимо от A: баланс строк, сохранение значений,
   дубликаты, неизвестные каналы и отсутствие настоящей связи с объектами.
4. Подготовь спецификацию синтетических воздействий и отрицательных контролей,
   а также критерии оценки до настройки детекторов. Приёмку M1 пройти вместе.

## Последовательность задач

| ID | Что сделать | Необходимый вход | Результат и приёмка |
|---|---|---|---|
| B1 | Аудит, тесты контрактов, спецификация испытаний | Исходники и маленькая общая выборка | Проверяемые требования к данным и сценариям |
| B2 | Генератор воздействий/контролей, тесты признаков | Существующий simulation и контракт A | Воспроизводимые сценарии, проверка 20 каналов вместе с A |
| B3 | Автомат эпизодов, восстановление, cooldown; оценка вида аномалии | Сначала искусственные scores, затем реальные A3 | Эпизод не дробится, повтор после восстановления находится |
| B4 | Закрытый synthetic holdout после заморозки методов | Версия A4 и заранее отделённый набор | Метрики по видам/типам, покрытие и решение допуска |
| B5 | High-confidence weak labels, normal/unknown, эпизоды | Только допущенные scores/методы | Версия разметчика, 50 positive-примеров и контрольные случаи |
| B6.1 | target 24h, наблюдаемость, temporal split/purge | Признаки A и эпизоды B5 | 0/1/null, нет уже начавшихся эпизодов и утечки |
| B6.2 | Baseline, Logistic Regression, CatBoost | Причинные train/validation features | Сравнение по одинаковой пригодной популяции |
| B7 | Пороги/калибровка, закрытый тест, объяснения, модельный inference | Замороженные модели и схема A | Metrics, feature importance/SHAP, predictions, пакет модели |

## Как работать параллельно

Пока A загружает историю, делай B1. Пока A строит признаки, делай B2.
На M3 сначала проверь автомат эпизодов на фиксированных последовательностях,
затем подключай оценки A по мере появления статистики, IF и кластеров.
Подготовить тесты target на вручную заданных эпизодах можно заранее;
обучать реальную модель до приёмки качества разметчика нельзя.

Твои файлы: `stage1/simulation.py`, `evaluation.py`, `verification.py`,
`episodes.py`, `forecast_labels.py`, новые `stage1/weak_labeling/`, `ml/forecast/`,
скрипты synthetic/evaluation/train/predict. Основной pipeline и признаки меняет A.
На каждое найденное нарушение передавай воспроизводимый пример владельцу модуля.

Техническая часть B2 выполнена в `docs/ml-b2-synthetic-report.md`: расширенный
генератор, независимые tuning/holdout, manifests и причинные проверки 20
синтетических каналов. Проверка конкретных часовых признаков остаётся точкой
объединения с A2.

Автономная часть B3 выполнена в `docs/ml-b3-score-episodes-report.md`:
причинный автомат scores → episodes, восстановление, отдельные уведомления,
cooldown и раздельная оценка факта/вида. После A3 остаётся подключить реальные
scores и выбрать параметры на tuning.

Существующее `ml/smoke_failure/` — прежнее исследование. Его цель «Неисправен»
не переносится автоматически в новый прогноз. Новая цель — подтверждённое
замороженными правилами начало псевдоэпизода в `(t,t+24h]`, при условии, что
эпизод ещё не начался. Отсутствие будущих наблюдений означает unknown, а не 0.

## Обязательные проверки

- Детектор обнаруживает воздействие после начала; прогноз предупреждает до начала.
  Это разные оценки и разные допустимые интервалы совпадения.
- Одинаковые фоновые фрагменты не попадают в tuning и holdout через разные seed.
  Эталонные поля сценария доступны оценке, но не модели.
- Один реальный/синтетический эпизод не создаёт множество TP. Повторы считаются отдельно.
- Добавление будущих данных не меняет признаки/прогноз в t. Future evidence
  может подтвердить метку, но не попасть в признаки.
- Preprocessing/детекторы/кластеры должны быть обучены на разрешённом прошлом;
  вместе с A организуй временные out-of-fold scores либо ранний fit-период.
- Порог и калибровка выбираются без финального test. Не изменяй определение
  псевдометки для улучшения прогнозных метрик после просмотра результатов.
- Никаких реальных Precision/Recall физического отказа без эталонной разметки.
  Реальные примеры оцениваются как объяснимость метода; экспертной проверки нет.

Каждый результат сопровождай тестами, командами, размерами/распределениями,
покрытием типов и ограничениями. После каждого milestone — совместная приёмка.
