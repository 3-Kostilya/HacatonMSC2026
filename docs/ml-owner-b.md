Участник A — друг; он отвечает за данные и признаки.

## Текущий этап после R6

R6 технически закрыт. Новая версия улучшения модели разрабатывается по
[протоколу B](ml-v2-experiment-protocol-b.md): A готовит причинные признаки и
допуск, B сравнивает модели и выбирает порог на train/validation. Старый test
не используется для подстройки; порог R6 остаётся исторической базой.

[Теневой пилот](ml-shadow-pilot-plan.md) — отдельная задача. B принял
[пакет P1/A](ml-shadow-pilot-a-replay-review.md) для исторического replay,
зафиксировал критерии P2/P3 и [независимо принял техническое восстановление
A/B](ml-shadow-pilot-b-checkpoint-acceptance.md), включая предупреждение и
сохранение cooldown. Далее нужно согласовать [контракт источника](ml-shadow-source-contract-draft.md).
Лимиты согласовать с заказчиком; модель и порог по прежнему test не менять.

Отдельно начат [эксперимент улучшения Q1](ml-quality-improvement-plan.md).
A подготовил полный train/validation-пакет с QA-коррекциями и 20 QA-счётчиками.
Пакет уже материализован: [отчёт A](ml-quality-improvement-a-review.md)
и [передача данных](ml-quality-improvement-handoff.md).
Следующая задача B: независимо проверить пакет, согласовать allowlist/QA-гейт
и протокол метрик ML v2 (A принял полный знаменатель Recall), затем сравнить базу и базу + QA
на одной популяции. Обучение и выбор порога — только train/validation;
старый открытый test не становится новым holdout. Исходные требования:
Precision > 0,7 и Recall > 0,5; улучшение пока не доказано.
Без расширения допуска основной Recall не выше 12,18%: Q1 — контроль
признаков, Q2 — необходимая совместная проверка новой причинной области.

## Что изменилось

Можно перейти к supervised-прогнозу зарегистрированных целевых состояний,
не дожидаясь кластеризации и алгоритмических псевдометок. Но новый справочник
не равен ground truth физического отказа: связи с наборами нет, покрытие низкое,
alarm не означает техническую неисправность.

Принятая для исследовательской версии цель по [контракту R1](ml-r1-operational-accepted.md):
новое зарегистрированное начало «Неисправен» в следующие 24 часа.
Иные технические состояния добавлять отдельной версией определения цели;
дым/движение/затопление не объединять с поломкой датчика по флагу тревоги.

## Первое задание — R1/B1

1. Принять аудит текущего CSV и классифицировать сообщения по категориям:
   normal, operational, environmental_alarm, technical_fault, unknown.
2. Написать проверяемые правила и отдельно их источник:
   dictionary_candidate / project_rule / unresolved. Работаем без новых файлов.
3. Зафиксировать target_kind, onset, восстановление, повтор, спорные секунды,
   недостаточную предысторию и наблюдаемость будущего.
4. С A проверить все уникальные строки CSV и частые/целевые состояния,
   которых в CSV нет; утвердить версию контрактов и fixtures.

«Неисправен» по точному тексту — допустимое определение наблюдаемого сообщения
для исследовательской цели. Оно не становится подтверждённой поломкой и не
выдаётся за полностью расшифрованное новым справочником состояние всех типов.

событий и правил R1. Не нужно ждать ни IsolationForest, ни кластеров.

## Главные условия разметки

- Повторные «Неисправен» внутри открытого состояния — один эпизод.
- Первая запись уже неисправна и предыстория неизвестна: начало не установлено.
- Молчание и alarm=false сами по себе не закрывают эпизод.
- Target в t = 1 при новом подходящем начале в (t,t+24h]; при активном
  эпизоде на t задача предсказания нового начала неприменима.
- Target = 0 требует возможности проверить отсутствие выбранного события,
  а не отсутствия строки в справочнике. Unknown не становится отрицательным классом.
- Предпосылки полноты журнала и наблюдаемости канала фиксируются отдельно.
  Справочник не создаёт отсутствующие будущие наблюдения.
- Определения зарегистрированного состояния и алгоритмической аномалии
  не смешиваются в одной цели и одном итоговом качестве.

Переиспользуй опыт B2/B3, но не применяй пороги score_episodes.py
механически к явным состояниям. Старый ml/smoke_failure — возможный источник
утилит/сравнения, не готовый результат новой задачи.

## Проверки моделей

Временное разделение фиксируется до настройки, целевые окна и подтверждения
не пересекают границы. Общая прошлая история окон сама по себе не является
утечкой; будущее сообщение в признаках является. Отбор 20 каналов для QA
не подходит в качестве готового train/test.

Прошлые состояния/alarm использовать можно, если они известны на t.
Обучать классификатор текущего alarm по тексту той же строки бессмысленно:
он воспроизведёт таблицу соответствий, а не предскажет будущее.

Твои файлы: предлагаемый stage1/state_labeling/, forecast_labels/target,
ml/forecast/, скрипты оценки/обучения/inference. Общие contracts согласовать с A.
Не редактировать его незавершённые features параллельно.

Отчёт: PR-AUC, эпизодные Precision/Recall, lead time, ложные предупреждения
на наблюдаемые дни, классы/эпизоды по типам, coverage/unknown. Вероятность
относится к зарегистрированному событию; физическую точность не заявлять.
Пороги и выбор модели только по validation, финальный test после заморозки.
